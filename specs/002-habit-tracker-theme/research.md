# Phase 0 Research: Habit Tracker & Theme System

## 1. Dark/light mode mechanism

- **Decision**: Switch Tailwind's `darkMode` from `'media'` (OS-preference-only, current state) to `'class'`. Dark mode is driven by a `.dark` class on `<html>`, set from the user's persisted preference — never from `prefers-color-scheme` alone. `<html>` also carries `data-theme="<theme-slug>"` for the color-theme layer (§2).
- **Rationale**: FR-009 requires defaulting every user to light mode regardless of OS preference, which `prefers-color-scheme`-only theming cannot express (a user with a dark-mode OS would always see dark on first load). A class/attribute-driven approach is also what's needed to let a signed-in user's DB-persisted choice win deterministically.
- **Alternatives considered**: Keep `darkMode: 'media'` and only add the color-theme layer — rejected, does not satisfy FR-009/FR-010 (explicit override + light default). Third-party theme library (`next-themes`) — rejected; this app has no other runtime npm dependencies for cross-cutting concerns like this (research.md precedent in 001-tasknihongo favors small hand-rolled solutions, e.g. the custom heatmap instead of a heatmap library), and the FOUC-avoidance mechanism needed here (§3) is simple enough to hand-roll against this project's existing Server Component conventions.

## 2. Color-theme layer (4 selectable palettes)

- **Decision**: Each theme row (`themes` table, §Data Model) stores a small fixed set of CSS custom-property values for **both** light and dark mode (mirroring the existing `--primary`/`--secondary`/`--accent`/`--background`/etc. pairs already hand-maintained in `globals.css`). At runtime, a `<style>` tag is generated server-side per request from the user's selected theme row, emitting `[data-theme="<slug>"] { --primary: ...; }` and `[data-theme="<slug>"].dark { --primary: ...; }` rules — i.e. the theme's colors are applied as an inline override layer on top of the existing `:root` defaults, not a full duplicate stylesheet. Non-color tokens (`--srs-again` etc., typography, spacing) are unaffected by theme choice; only the palette-defining variables (`--primary`, `--primary-foreground`, `--secondary`, `--secondary-foreground`, `--accent`, `--accent-foreground`) are theme-controlled, since those are what visually distinguish an accent/brand palette. `--background`/`--foreground`/`--card`/`--border`/`--muted`/`--success`/`--warning`/`--danger` stay governed purely by light/dark mode (`.dark` class), identical across all 4 themes, so status colors and surfaces stay consistent regardless of which brand palette a user picks (dataviz-skill-aligned: status colors are reserved and never themed).
- **Rationale**: Keeps the diff small (touches only the brand-accent variables that already vary between the shipped teal/orange light and dark values), keeps status/surface tokens consistent (no risk of a theme accidentally shipping unreadable danger/warning colors), and satisfies FR-012 (DB-driven, not hardcoded) without a rewrite of every component's className.
- **Alternatives considered**: Full per-theme Tailwind config / separate CSS bundles per theme — rejected, massive build-time complexity for 4 palettes that only need ~6 variables each. Storing colors as a single JSON blob column — rejected in favor of explicit typed columns (§Data Model) so admin form validation (US3) and the server-rendered `<style>` generation stay simple and typo-proof.

## 3. Avoiding a flash of the wrong theme (SC-005) + cross-device re-apply (SC-004)

- **Decision**: On every mode/theme change, `POST /api/appearance` writes both to the DB (`user_appearance_preferences`, owner-scoped upsert) **and** to a `theme` cookie (JSON: `{mode, themeSlug}`, `sameSite: lax`, long expiry) in the same response, so the cookie and DB never drift. The root layout (`app/layout.tsx`, a Server Component) reads the cookie synchronously (Next.js `cookies()`) and renders `<html class={mode==='dark' ? 'dark' : ''} data-theme={themeSlug}>` before any client JS runs — no client-side "hydrate then flip" step, so there's no flash. For the cross-device/cross-browser case (a session exists but this browser has no cookie yet — fresh sign-in, cleared cookies, etc.), `middleware.ts` — which already runs on every request and already reads the session (001-tasknihongo research.md §1) — checks for the `theme` cookie and, if absent, reads `user_appearance_preferences` and sets it on the response before the page renders. This is a single choke point that covers every entry path (login, signup, magic-link/OAuth callback, direct URL) instead of duplicating cookie-priming logic per auth flow, and satisfies SC-004's "within 1 page load."
- **Rationale**: This project already reads auth state server-side in `app/(app)/layout.tsx` and `middleware.ts` per research.md §1 of 001-tasknihongo — reading/priming a cookie server-side in middleware and the root layout is the same pattern applied to appearance instead of auth, and requires no client-side flash-prevention script.
- **Alternatives considered**: `localStorage`-only (no server read) — rejected, causes an unavoidable flash on first paint since Server Components can't read `localStorage`, and doesn't satisfy "tied to their account" (FR-013) for a fresh browser. Priming the cookie from each auth entry point individually (login page, signup, callback route) instead of middleware — rejected, duplicates the same read-and-set logic across 3+ places for no benefit over one middleware check. DB-only (read on every Server Component render, no cookie) — rejected as an unnecessary DB round-trip on every single page's root layout render purely to answer "light or dark"; the cookie is a cache of the DB row kept authoritative by always writing both together.

## 4. Habit grid data & month-window queries

- **Decision**: `habits` (id, user_id, name, created_at) and `habit_completions` (habit_id, user_id, completion_date, created_at; unique on `(habit_id, completion_date)`) as two owner-scoped tables, same RLS shape as every other owner-scoped table in this project (`boards`, `notes`, etc.). Ticking a day is `INSERT ... ON CONFLICT (habit_id, completion_date) DO NOTHING` (mark done) or `DELETE ... WHERE habit_id = ? AND completion_date = ?` (un-mark) — no boolean "completed" column needed, since row-existence *is* completion (same modeling reasoning as `user_vocab_progress`'s lazy-row pattern elsewhere in this codebase, applied to "did this happen on this day" instead of "what's the SRS state"). The month view queries `habit_completions` for the visible habit set with `completion_date BETWEEN <month start> AND <month end>`, grouped client-side by `habit_id`.
- **Rationale**: Matches this project's established conventions (direct-to-Supabase client mutations under RLS for simple owner-scoped CRUD, per every other feature/*/components manager in this codebase) rather than introducing a new API route for what's a straightforward toggle. Row-existence-as-completion avoids a redundant boolean that could theoretically desync from row presence.
- **Alternatives considered**: A single `completed: boolean` column with one row per habit per day pre-created — rejected, requires pre-populating rows for the whole visible range (extra writes, extra migration complexity) for no behavioral gain over row-existence.

## 5. Per-habit streak indicator (FR-008)

- **Decision**: Computed client-side (or in the Server Component fetching the month's data) from the fetched `habit_completions` rows already in memory for the visible month — a simple consecutive-day count walking backward from today (or from the last day of a past month being viewed) — no new DB aggregation function needed, no dependency on `features/study-plan/lib/heatmap.ts` (that module is scoped to SRS `review_logs` streaks per 001-tasknihongo's own Assumptions, and this feature's spec explicitly keeps habits data-independent from SRS activity).
- **Rationale**: The visible month's data is already fetched for rendering the grid; deriving the streak from it avoids a second query. A pure function co-located with the habit feature (mirroring `study-plan/lib/heatmap.ts`'s own pattern of pure, testable aggregation helpers) keeps this consistent with the codebase's existing style without reusing SRS-specific code across an intentionally separate domain.

## 6. Admin theme management surface

- **Decision**: `GET/POST/PUT/DELETE /api/admin/reference-data/themes`, grouped alongside the existing `/api/admin/reference-data/{vocab,grammar,confusable-pairs}` routes (same service-role-client, same admin-role-gated pattern), plus a themes section on the existing `app/admin/reference-data/page.tsx` (or a new tab there) rather than a whole new admin route.
- **Rationale**: Themes are global reference data exactly like vocab/grammar — same ownership shape (`admin`-writable, all-authenticated-users-readable), same CRUD shape. Reusing the existing reference-data admin surface avoids duplicating the admin-role-gate/service-role-client plumbing for a fourth near-identical CRUD screen.
- **Alternatives considered**: A dedicated `/admin/themes` page — rejected as unnecessary surface-area growth for one more reference table that fits the existing reference-data page's pattern.
